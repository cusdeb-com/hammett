**Экран** — это абстракция над обычным Telegram-сообщением для управления его состоянием. Экраны представляют собой классы, которые наследуются от класса [`Screen`](../api_reference/core/screen.md#hammett.core.screen.Screen) из модуля [`hammett.core.screen`](../api_reference/core/screen.md). Этот класс решает две в равной степени важные задачи:

1. предоставление возможности для отрисовки и дальнейшей перерисовки контента;
2. предоставление механизма перехода от одного экрана к другому.

Экран может состоять из следующих компонентов, которые представлены соответствующими атрибутами класса [`Screen`](../api_reference/core/screen.md#hammett.core.screen.Screen):

1. `cover` или `document` — обложка (изображение) или документ, которые должны быть отправлены в чат пользователю. Если экран имеет обе эти составляющие, приоритет у **документа** будет выше, поэтому он отправится пользователю в чат, а изображение будет проигнорировано.
2. `description` — текст сообщения, который может содержать HTML-теги (см. [здесь](https://core.telegram.org/api/entities#allowed-entities), какие теги могут использоваться в описаниях).
3. `keyboard` — одна или более кнопок, формирующих клавиатуру экрана (см. [Клавиатура и кнопки](#клавиатура-и-кнопки)).

У экрана должен быть _хотя бы один_ из следующих компонентов: обложка (`cover`), описание (`description`) или документ (`document`).

> **Примечание**: на экране эти компоненты располагаются строго в том порядке, в котором они перечислены в списке выше. Повлиять на этот порядок **нельзя**.

<!-- -->

> **Примечание**: максимальное количество кнопок на клавиатуре по горизонтали составляет **8**. Общее количество кнопок, отображаемых одновременно, составляет **100**. Используйте [этот](https://handbook.tmat.me/en/messages/buttons#button-layouts) источник в качестве дополнительного, чтобы перепроверить эту информацию.

## <a name="настройка-компонентов-экранов"></a> Настройка компонентов экранов

У экрана есть атрибуты, которые позволяют настраивать его компоненты:

1. **Кеширование обложек**. Если большинство экранов бота используют одну и ту же обложку, можно включить ее кеширование, чтобы ускорить рендеринг экранов. Для этого нужно атрибут `cache_covers` установить в `True`. Таким образом, указанная обложка будет кешироваться вне зависимости от того, что атрибуту `cover` передано: URL на внешний ресурс или путь к файлу.
2. **Уточнение формата описаний**. Атрибут `html_parse_mode` указывает, в каком формате передан атрибута `description` текст описания экрана: в HTML или Markdown.
3. **Скрытие клавиатуры**. В некоторых случаях может потребоваться скрывать клавиатуру у экранов, которые остаются в истории. Для этого нужно атрибут `hide_keyboard` установить в `True` (см. [Скрытие клавиатуры](#скрытие-клавиатуры)).

### <a name="источники-действий-и-его-типы"></a> Источники действий и его типы

У каждой кнопки есть атрибут `source`, который позволяет связать кнопку с ее действием или обработчиком. Этот атрибут указывает на _источник действия_, которое должно быть выполнено при нажатии на кнопку.

Наряду с атрибутом `source` есть также атрибут `source_type`, название которого говорит само за себя — он необходим для уточнения типа того или иного источника.

В роли _источника_ (source) могут выступать:

<!-- prettier-ignore-start -->

1. **Экран**. Он предназначен для перехода на указанный экран.

      Для этого источника используются следующие типы источников:

      - `MOVE_SOURCE_TYPE` — нужен для перехода с текущего экрана на другой с его **перерисовкой** на новый экран. Является оберткой для вызова следующего кода:

         {% include-markdown 'examples/screens/move_shortcut.md' %}

      - `JUMP_SOURCE_TYPE` — нужен для перехода с текущего экрана на другой с отправкой другого экрана в виде **нового сообщения**. Является оберткой для вызова следующего кода:

         {% include-markdown 'examples/screens/jump_shortcut.md' %}

      - `MOVE_ALONG_ROUTE_SOURCE_TYPE` — нужен для перехода с текущего экрана на другой с его **перерисовкой** на новый экран, когда текущий экран зарегистрирован в одном состоянии, а другой — в другом состоянии. Является оберткой для вызова следующего кода:

         {% include-markdown 'examples/screens/move_along_route_shortcut.md' %}

      - `JUMP_ALONG_ROUTE_SOURCE_TYPE` — нужен для перехода с текущего экрана на другой с отправкой другого экрана в виде **нового сообщения**, когда текущий экран зарегистрирован в одном состоянии, а другой — в другом состоянии. Является оберткой для вызова следующего кода:

2. Метод экрана, зарегистрированный в качестве **обработчика** (см. [Обработчики](#обработчики)). Он предназначен для выполнения кода внутри этого метода.

### <a name="скрытие-клавиатуры"></a> Скрытие клавиатуры

Когда для перехода от одного экрана к другому используется метод [`jump`](../api_reference/core/screen.md#hammett.core.screen.Screen.jump), то экран, на который осуществляется переход, появляется в виде _нового сообщения_, а экран, с которого осуществился переход, остается в истории (см. [Переходы между экранами](#переходы-между-экранами)). Hammett дает разработчикам возможность _автоматически скрывать_ клавиатуру у экранов, которые остаются в истории, сохраняя ее только у _последнего экрана_. Это делает историю сообщений более чистой и избавляет от потенциальных ошибок, которые могут возникнуть, когда пользователь нажимает на кнопки предыдущих сообщений.

Чтобы включить скрытие клавиатуры, параметр конфигурации `SAVE_LATEST_MESSAGE` и атрибут `hide_keyboard` у каждого из экранов должны быть установлены в `True`. Для реализации последнего рекомендуется использовать **базовый экран** (см. [Лучшие практики](best-practices.md#базовые-экраны)).

Однако заметьте, что удаление клавиатуры у более чем одного предыдущего сообщения **не поддерживается**. Поэтому, если вы включите эту возможность через какое-то время _после_ запуска вашего бота, не следует ожидать, что клавиатуры всех экранов, сохранившихся в истории, скроются сразу после следующего вызова [`jump`](../api_reference/core/screen.md#hammett.core.screen.Screen.jump).

> **Примечание**: данная возможность не всегда может корректно работать в **веб-версии Telegram**. Там возможен случай, когда клавиатура экрана сохраняется, но перестает работать. Чтобы это исправить, нужно обновить страницу браузера. В приложении эта проблема встречается реже. Также имейте в виду, что **нельзя гарантировать** 100% работоспособность этого механизма из-за возможных проблем на стороне Telegram.

См. live-пример бота [HammettHideKeyboardBot](https://t.me/HammettHideKeyboardBot) с демонстрацией работы этого функционала.

## <a name="переходы-между-экранами"></a> Переходы между экранами

Базовый класс [`Screen`](../api_reference/core/screen.md#hammett.core.screen.Screen) предоставляет своим наследникам два следующих метода для стандартного перехода между экранами:

1. [`move`](../api_reference/core/screen.md#hammett.core.screen.Screen.move) используется, когда нужно перейти от текущего экрана к другому, тем самым **перерисовав** текущий;
2. [`jump`](../api_reference/core/screen.md#hammett.core.screen.Screen.jump) используется, когда нужно перейти от одного экрана к другому, тем самым отправив этот экран в виде **нового сообщения** и сохранив предыдущее в истории.

Например, есть экран `First` с кнопкой, которая ведет на `Second`.

{% include-markdown 'examples/screens/moving_between_screens.md' %}

При нажатии на кнопку "Next ➡️" экран `First` будет перерисован, и на его месте окажется экран `Second`, т.е. `First` "сотрется" из истории. ## <a name="обработчики"></a> Обработчики

Обработчики — это методы экранов, которые вызываются при возникновении определенных событий: нажатие на кнопку, отправка изображения в чат с ботом и т.д.

Hammett реализует четыре типа обработчиков:

1. обработчик нажатия на кнопку;
2. обработчик общего ввода;
3. обработчик текстового ввода;
4. обработчик команды (например, `/say_hello`).

Чтобы сделать из обычного метода экрана обработчик, этот метод необходимо **зарегистрировать**. Для этого нужно применить к нему соответствующий **декоратор** определенного типа и к его аргументу `self` добавить еще **два позиционных аргумента** (их порядок важен) — `update` и `context`.

> **Примечание**: обработчики не могут быть статическими методами или методами класса, т.е. обернуты в [`staticmethod`](https://docs.python.org/3/library/functions.html#staticmethod) и [`classmethod`](https://docs.python.org/3/library/functions.html#classmethod) соответственно.

<!-- -->

> **Примечание**: независимо от типа обработчика, все они должны возвращать какое-то состояние (см. [Состояния](states.md)), например, `DEFAULT_STATE` из модуля [`hammett.core.constants`](../api_reference/core/constants.md).

Теперь давайте разберем каждый из этих типов обработчиков по отдельности.

Чтобы конкретизировать тип контента, на который обработчик будет срабатывать, нужно в качестве аргумента `filters` передать ему тип контента из пакета `telegram.ext.filters` (см. [Filters](https://docs.python-telegram-bot.org/en/v21.7/telegram.ext.filters.html)).

Для регистрации обработчика используется декоратор `register_input_handler` из модуля [`hammett.core.handlers`](../api_reference/core/handlers.md).

Если вы хотите, чтобы этот обработчик срабатывал на определенном этапе/этапах взаимодействия пользователя с ботом, то класс экрана, в котором он определен, следует зарегистрировать только в этом/этих состояниях; в противном случае — во всех имеющихся состояниях (см. [Состояния](states.md)).

## <a name="работа-с-документами"></a> Работа с документами

Чтобы прикрепить документ к экрану, нужно заполнить атрибут `document` класса [`Screen`](../api_reference/core/screen.md#hammett.core.screen.Screen). Он представляет собой типизированный словарь с двумя ключами: `media` и `document_kwargs`. Значением `media` является сам документ в байтовом виде, а `document_kwargs` — словарь с дополнительными атрибутами объекта `InputMediaDocument`. С его помощью можно задать имя документа с расширением, передав ключ `filename`. Все возможные ключи можно посмотреть в документации к [`InputMediaDocument`](https://docs.python-telegram-bot.org/en/v21.5/telegram.inputmediadocument.html).
