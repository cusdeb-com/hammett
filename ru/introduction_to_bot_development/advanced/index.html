    Расширенные возможности

    Hammett предоставляет дополнительные инструменты, которые помогают расширять функциональность бота. Этот раздел описывает несколько полезных механизмов, которые можно использовать при разработке комплексных ботов. Изучать его следует после ознакомления с базовыми возможностями фреймворка.

    Сохранение контекста#

    Когда пользователь инициирует разговор с ботом (к примеру, посредством команды /start), бот находится в исходном состоянии None (см. Состояния). Далее пользователь может переключать бота между разными состояниями — это определяет, как бот будет себя вести в дальнейшем.

    Контекст взаимодействия между пользователем и ботом используется для хранения данных, связанных с пользователем, чатом или состоянием бота и хранится на стороне бота в оперативной памяти. Таким образом, пользователь может продолжить работу с ботом в любой момент с того места, на котором остановился, но только до тех пор, пока бот не будет перезапущен (на сервере). Как только бот перезапускается, контекст теряется, и пользователю требуется снова инициировать разговор с ботом с помощью команды /start. В промышленной среде такое недопустимо: перезапуск ботов не должен влиять на пользователей.

    Решение: Redis Persistence#

    Для восстановления контекста после перезапуска Hammett предлагает механизм под названием Redis Persistence. Он сохраняет данные контекста в базу Redis / Valkey при выключении бота и загружает его обратно в бота при старте. Для того чтобы включить этот механизм, добавьте следующий атрибут в settings.py:

    REDIS_PERSISTENCE = {
    'HOST': '127.0.0.1',
    'PORT': 6379,
    'DB': 0,
    'PASSWORD': None,
}

    Здесь перечислены параметры подключения к Redis / Valkey. Затем нужно поднять сервер Redis / Valkey, например, в Docker-контейнере следующей командой:

    docker run -d --rm -p 6379:6379 --name redis redis

    После этого нужно передать в аргумент persistence объекта класса Bot экземпляр класса RedisPersistence из модуля hammett.core.persistence (см. Сборка бота и запуск):

    from hammett.core import Bot
from hammett.core.persistence import RedisPersistence


Bot(
    # There might be some other attributes here
    persistence=RedisPersistence(),
)

    Существует два режима сброса контекста в Redis / Valkey: перед остановкой бота и на каждое действие пользователя. Режим можно выбрать с помощью аргумента on_flush при создании объекта класса RedisPersistence. Этот аргумент принимает значения True или False. Значение по умолчанию — False, т.е. сброс данных в Redis / Valkey происходит на каждое действие пользователя.

    Примечание: чтобы бот корректно завершал свои процессы и успешно сбрасывал свое состояние, используйте сигнал SIGTERM для завершения процесса бота. Важно отметить, что при использовании сигнала SIGKILL процесс мгновенно завершится, и состояние не будет сохранено.

    Задачи, выполняемые по расписанию#

    Задачи, выполняемые по расписанию, позволяют с определенной периодичностью или по расписанию отправлять пользователям ботов уведомления (notifications) — любые экраны, в том числе виджеты. Они представляют собой асинхронные функции, принимающие один аргумент — context. Как и обработчики, эти функции должны быть зарегистрированы. Регистрация осуществляется при создании объекта класса Bot (см. Сборка бота и запуск). Эту функцию нужно передать в качестве аргумента параметру job_configs, типизация которого описана в модуле hammett.types:

    from typing import Any, TypedDict
from telegram._utils.types import JSONDict
from telegram.ext import CallbackContext
from telegram.ext._utils.types import JobCallback


class JobConfig(TypedDict):
    callback: JobCallback[CallbackContext[Any, Any, Any, Any]]
    job_kwargs: JSONDict

    Этот параметр представляет собой словарь с обязательными ключами callback и job_kwargs. Значением ключа callback является та самая задача (асинхронная функция), а job_kwargs представляет собой словарь для ее конфигурации. Возможные ключи для конфигурации перечислены здесь. Среди них обязательным является ключ trigger, который может принимать одно из следующих значений: date, interval или cron.

    Примечание: под капотом Hammett использует run_custom класса JobQueue.

    Например, ниже представлен обработчик задачи, который каждый час шлет пользователю в чат сообщение. Вот как будет выглядеть его регистрация при создании объекта класса Bot:

    from hammett.core import Bot


Bot(
    # There might be some other attributes here
    job_configs=[
        {
            'callback': send_message_per_hour,
            'job_kwargs': {
                'trigger': 'interval',
                'seconds': 60 * 60,
            },
        },
    ],
)

    Вызов экранов в обработчиках задач#

    Если понадобиться вызвать экран из обработчика задачи, выполняемой по расписанию, то сделать это с помощью методов move и jump не получится, т.к. в обработчике задачи нет доступа к обязательному для них объекту Update. В этом случае следует использовать метод send.

    Вот так выглядит простой экран, который будет отправляться пользователям в качестве уведомления:

    from hammett.core import Screen


class Notification(Screen):
    cover = 'https://some/url/path/to/image.jpg'
    description = 'Another hour has passed.'

    А вот так выглядит сам обработчик:

    from hammett.core import Button
from hammett.core.constants import RenderConfig, SourceTypes


async def send_message_per_hour(context):
    users = await get_users()  # For example, from Redis or API
    for user in users:
        config = RenderConfig(
            chat_id=user['telegram_id'],
            keyboard=[[
                Button('⬅️ Main Menu', MainMenu,
                       source_type=SourceTypes.MOVE_SOURCE_TYPE),
            ]]
        )
        await Notification().send(context, config=config)

    В приведенном примере экран Notification должен быть зарегистрирован во всех состояниях, чтобы после того как пользователь получит сообщение, он смог вызвать обработчики кнопок на клавиатуре этого сообщения (см. Регистрация обработчиков).

    Примечание: метод send также поддерживается виджетами, что позволяет их тоже использовать в качестве уведомлений (см. Виджеты).

    Примечание: если кнопка на клавиатуре экрана, вызванного из обработчика задачи, имеет полезную нагрузку, то для нее обязательно должен быть указан аргумент chat_id (см. Кнопки в уведомлениях).

    Управление отрисовкой (метод render)#

    В Hammett любая отрисовка экранов сводится к вызову их метода render. Переопределение метода может понадобиться, если необходимо добавить какую-то логику перед каждой отрисовкой экрана вне зависимости от того, через какой обработчик — move, jump, move_along_route, jump_along_route, send или start — он был вызван.

    Например, в демо HammettQuizBot метод render переопределяется для сброса текущего вопроса и общего количества правильных ответов после перехода на главное меню: не имеет значения, как был вызван экран главного меню, состояния опроса будут сброшены после перехода на него.

    Хранение данных пользователя на стороне бота#

    Комплексному боту требуется хранить на своей стороне различную информацию, связанную с пользователями. В простейшем случае это могут быть данные для постраничного перехода. Например, в боте есть 50 разделов с книгами, которые разбиваются по пять на один экран, и пользователь просматривает их, нажимая кнопки "Назад" и "Вперед". Чтобы реализовать это, необходимо каждый раз сохранять номер текущего экрана в хранилище на стороне бота, которое закреплено за конкретным пользователем, где действия других пользователей никак не влияют на него.

    С этим хранилищем можно работать через context.chat_data, когда нужно хранить информацию, специфичную для каждого чата, и context.user_data, когда нужно хранить информацию, специфичную для каждого пользователя. С их помощью вы можете сохранять информацию, полученную в одном обработчике, и передавать ее в другой, выполняя над ними операции, как над обычными словарями. Ниже приведен пример, как сохранить полученную полезную нагрузку для ее "безопасного" извлечения из хранилища:

    from hammett.core.constants import DEFAULT_STATE, RenderConfig
from hammett.core.exceptions import FailedToGetDataAttributeOfQuery, PayloadIsEmpty
from hammett.core.handlers import register_button_handler
from hammett.core.mixins import StartMixin

MY_PAYLOAD_KEY = 'my_payload_key'


class MainMenuScreen(StartMixin):
   async def get_payload_safely(self, update, context, key):
       try:
           payload = await self.get_payload(update, context)
       except (FailedToGetDataAttributeOfQuery, PayloadIsEmpty):
           try:
               payload = context.user_data[key]
           except KeyError:
               raise
       else:
           context.user_data[key] = payload

       return payload

   @register_button_handler
   async def handle_button_click(self, update, context):
       payload = await self.get_payload_safely(update, context, MY_PAYLOAD_KEY)

       await self.render(update, context, config=RenderConfig(description=payload))
       return DEFAULT_STATE

    Таким образом, если произойдет сбой на стороне Telegram и пользователь повторно нажмет на кнопку, то будет выброшено исключение PayloadIsEmpty (см. Полезная нагрузка), после чего будет получена и возвращена полезная нагрузка, сохраненная в словаре context.user_data под ключом MY_PAYLOAD_KEY.

    Также существует словарь context.bot_data, с которым можно работать по тому же принципу, но в отличие от context.chat_data и context.user_data, это единственный словарь для вашего бота.

    Примечание: все данные, записанные в context.bot_data, context.chat_data и context.user_data, хранятся в оперативной памяти и удаляются после завершения процесса бота. Для того чтобы сохранять их между перезапусками бота, используйте сохранение контекста.

    Примечание: если вы используете сохранение контекста, то данные, сохраняемые в context.bot_data, context.chat_data и context.user_data, должны поддерживать сериализацию и десериализацию. Это связано с тем, что встроенная реализация сохранения состояния может работать только с сериализуемыми данными.

    Примечание: у вас может появиться соблазн использовать атрибуты класса Screen для сохранения каких-то данных, специфичных для каждого пользователя. Однако этого делать нельзя, т.к. экраны являются синглтонами. Это означает, что изменение значения атрибута одним пользователем ведет к изменению его значения у всех пользователей.

    from hammett.core.handlers import register_button_handler


@register_button_handler
async def handle_payment(self, update, _context):
    if has_paid(update.effective_user.id):
        self.description = 'You have successfully paid'

    Работа с API#

    Каждый компонент экрана можно запросить через API, сделав экран полностью динамическим. Ключом к полной динамичности является RenderConfig.

    RenderConfig — это класс данных (dataclass), используемый для формирования компонентов экрана, которые в дальнейшем будут использованы в процессе его отрисовки. Для этого достаточно инициализировать объект класса RenderConfig и задать его атрибутам значения либо через точечную нотацию, либо непосредственно при инициализации:

    from hammett.core import Button
from hammett.core.constants import RenderConfig, SourceTypes


config = RenderConfig()
config.description = 'Your description'
config.keyboard = [[
    Button(
        'Your button',
        'https://github.com/cusdeb-com/hammett',
        source_type=SourceTypes.URL_SOURCE_TYPE,
    ),
]]

    или

    from hammett.core import Button
from hammett.core.constants import RenderConfig, SourceTypes

config = RenderConfig(
   description='Your description',
   keyboard=[[
       Button(
           'Your button',
           'https://github.com/cusdeb-com/hammett',
           source_type=SourceTypes.URL_SOURCE_TYPE,
       ),
   ]]
)

    После этого нужно передать заполненный RenderConfig методу отрисовки (см. Управление отрисовкой (метод render)) и не забыть вернуть какое-нибудь состояние, например, DEFAULT_STATE.

    Рассмотрим пример с магазином, где нужно запросить список товаров, на основе которого будет построена клавиатура с их названиями. Если товаров нет, пользователю должно быть отправлено сообщение об ошибке.

    Вот как может выглядеть код для решения описанной задачи:

    import json
import httpx

from hammett.core import Button, Screen
from hammett.core.constants import DEFAULT_STATE, RenderConfig, SourceTypes


class ListOfProducts(Screen):
    async def move(self, update, context, **kwargs):
        keyboard = []
        try:
            response = await httpx.AsyncClient().get('https://some/url/path/to/products/')
            products = response.json()
        except (json.JSONDecodeError, httpx.HTTPError):
            config = RenderConfig(description="Couldn't fetch the products")
        else:
            config = RenderConfig(description='Here are the products:\n')
            keyboard = [
                [
                    Button(f'{product["title"]}',
                           SelectedProduct,
                           source_type=SourceTypes.MOVE_SOURCE_TYPE)
                ] for product in products
            ]

        config.keyboard = [
            *keyboard,
            [Button('Main Menu', MainMenu,
                   source_type=SourceTypes.MOVE_SOURCE_TYPE)],
        ]

        await self.render(update, context, config=config)
        return DEFAULT_STATE

    В приведенном примере код будет выполняться при вызове обработчика move у объекта Screen. Это означает, что если экран будет вызван с помощью обработчика jump, выполнение не дойдет до описанной логики. Такой подход позволяет более детально настраивать, что и в каких случаях следует отрисовывать. Однако, если такая тонкая настройка не нужна, можно задать требуемое поведение в одном месте — в методе get_config. Этот метод вызывается в каждом из встроенных обработчиков (за исключением send, т.к. ему необходимо передавать конфигурацию явно через аргумент) перед передачей конфигурации методу отрисовки.

    Вот как будет выглядеть этот же код, но уже с использованием get_config:

    import json
import httpx

from hammett.core import Button, Screen
from hammett.core.constants import RenderConfig, SourceTypes


class ListOfProducts(Screen):
    async def get_config(self, update, context, **kwargs):
        keyboard = []
        try:
           response = await httpx.AsyncClient().get('https://some/url/path/to/products/')
           products = response.json()
        except (json.JSONDecodeError, httpx.HTTPError):
           config = RenderConfig(description="Couldn't fetch the products")
        else:
           config = RenderConfig(description='Here are the products:\n')
           keyboard = [
               [
                   Button(f'{product["title"]}',
                          SelectedProduct,
                          source_type=SourceTypes.MOVE_SOURCE_TYPE)
               ] for product in products
           ]

        config.keyboard = [
           *keyboard,
           [Button('Main Menu', MainMenu,
                  source_type=SourceTypes.MOVE_SOURCE_TYPE)],
        ]

        return config

    Как видно из примера, в методе get_config не требуется вызывать метод отрисовки или возвращать состояние. Вместо этого нужно вернуть сам объект RenderConfig.

    Важно отметить, что использование RenderConfig для компоновки экрана будет иметь самый высокий приоритет при отрисовке, даже если переопределен метод get_description или установлен статический атрибут description.

    Для наглядности вот иерархия трех разных способов компоновки экрана:

    Stopwatch#

    Hammett предлагает встроенный механизм под названием Stopwatch для отслеживания времени выполнения обработчиков. Он помогает находить узкие места в работе бота и понимать, где именно требуется оптимизация.

    Для активирования этой возможности необходимо установить параметр конфигурации HANDLERS_STOPWATCH в True (значение по умолчанию — False).

    Hammett имеет два вида процессоров. Они представляют собой классы, которые находятся в модуле hammett.stopwatch.stats и реализуют логику отображения статистики:

    1. PrintStatsProcessor выводит статистику по обработчикам в консоль с помощью функции print и является процессором по умолчанию. Вот пример результата его работы:
    MyScreen.move:
  CPU time: 0.010832668000000045
  Select time: 0.17263412475585938
  Other IO time: 0.0
  Real time: 0.18328166007995605
    1. JsonStatsProcessor записывает статистику по обработчикам в файл handler_stats.json после завершения процесса бота. Вот пример результата его работы:
    {
  "MainMenu.move": [
    {
      "cpu_time": 0.014320042000000033,
      "select_time": 0.1973109245300293,
      "other_io_time": 0.0,
      "real_time": 0.21143460273742676
    }
  ]
}

    Выбранный процессор нужно указать в параметре конфигурации STOPWATCH_STATS_PROCESSOR, в котором по умолчанию содержится 'hammett.stopwatch.stats.PrintStatsProcessor'.

    Вебхуки#

    Существует два способа получения обновлений от сервера Telegram: поллинг (polling) и вебхук (webhook). По умолчанию боты используют поллинг, опрашивая сервер Telegram на наличие обновлений в процессе работы. Поллинг универсален: он подходит как для разработки, так и для эксплуатации бота в промышленной среде. Но за универсальность приходится платить задержками, которые могут отразиться на отзывчивости бота, т.к. обновления не поступают в режиме реального времени.

    Вебхук, в свою очередь, позволяет автоматически получать обновления от сервера Telegram через выставленный ботом URL, на который в случае появления обновлений отправляются POST-запросы. Вебхук подходит исключительно для эксплуатации бота в промышленной среде и гарантирует получение обновлений в режиме реального времени.

    Для того чтобы переключиться на этот способ получения обновлений, необходимо указать несколько параметров конфигурации и настроить веб-сервер. Ниже приведен пример settings.py для настройки вебхука:

    import os

# получать обновления через webhook
USE_WEBHOOK = os.getenv('USE_WEBHOOK', '').lower() == 'true'

# номер порта, на котором будет прослушиваться входящий трафик
WEBHOOK_PORT = int(os.getenv('WEBHOOK_PORT', '5000'))

# IP-адрес или имя хоста, на котором будет работать сервер
WEBHOOK_LISTEN = os.getenv('WEBHOOK_LISTEN', 'example.com')

# путь, по которому Telegram будет отправлять обновления боту
WEBHOOK_URL_PATH = os.getenv('WEBHOOK_URL_PATH', '')

# (опционально) полный URL, который Telegram будет использовать для отправки обновлений
WEBHOOK_URL = os.getenv('WEBHOOK_URL', 'https://example.com')

    И пример конфигурации для Nginx:

    server {
    listen 443 ssl;
    server_name example.com;
    ssl_certificate cert.pem;
    ssl_certificate_key private.key;

    location / {
        proxy_pass http://127.0.0.1:5000;
    }
}

    Декоратор cache#

    В Hammett реализован механизм кеширования на базе Redis / Valkey. С его помощью можно кешировать результаты работы функций и методов, которые делают запросы к различным API.

    Для конфигурации кеша используется параметр конфигурации REDIS_CACHE. Его обязательным ключом является DB, который указывает на номер базы данных для записи и хранения кешированных данных. Вот пример:

    REDIS_CACHE = {
    'HOST': '127.0.0.1',
    'PORT': 6379,
    'PASSWORD': None,
    'DB': 1,
}

    Механизм кеширования также позволяет указать время жизни кеша (TTL, Time-To-Live) в секундах или сбросить кеш принудительно.

    Ниже приведен пример класса ApiClient с методом get_caption для запроса описания экрана через API, результат выполнения которого кешируется на час:

    import httpx
from hammett.core.cache import cache


class ApiClient:
    def __init__(self):
        self._session = httpx.AsyncClient()

    @cache(60 * 60)
    async def get_caption(self):
        return await self._session.get('https://your/path/to/url/')

    Вызов этого метода выглядит так:

    caption = await ApiClient().get_caption()

    Пример выше можно доработать и добавить возможность сброса кеша:

    import httpx
from hammett.core.cache import cache


class ApiClient:
    def __init__(self):
        self._session = httpx.AsyncClient()

    @cache(60 * 60)
    async def _get_caption_with_cache(self, *_args, **_kwargs):
        return await self._session.get('https://your/path/to/url/')

    async def get_caption(self, drop_cache=False):
        if drop_cache:
            return await self._get_caption_with_cache('https://your/path/to/url/', drop_cache=drop_cache)

        return await self._get_caption_with_cache('https://your/path/to/url/')

    Это решение обратно совместимо с предыдущим, т.е. описание экрана как и раньше можно получать, выполнив

    caption = await ApiClient().get_caption()

    Но теперь, если потребуется сбросить кеш, get_caption() можно вызвать следующим образом:

    caption = await ApiClient().get_caption(drop_cache=True)

    Примечание: если необходимо получить доступ к кешу (например, для того чтобы реализовать экран для ручного сброса кеша администратором), то его можно импортировать из модуля hammett.core.cache и работать с ним напрямую.

    Например, вот так может выглядеть обработчик сброса кеша:

    from hammett.core.cache import CACHE_REDIS_CLI
from hammett.core.handlers import register_button_handler


@register_button_handler
async def drop_cache(self, update, context):
    await CACHE_REDIS_CLI.flushdb()

    return await CacheDroppingSuccess().move(update, context)

    Функция render_template_from_string#

    Функция render_template_from_string представляет собой готовый инструмент для формирования динамических описаний экрана с помощью шаблонного движка Jinja2.

    Функция принимает два аргумента — шаблон (template) и контекст (context). Шаблон может содержать переменные, которые имеют следующий вид: {{ variable }}. В результате работы функции переменные будут заменены на значения, взятые из контекста. Контекст представлен словарем: его ключами являются названия переменных, а значениями — текст для подстановки.

    Ниже приведен пример использования для формирования описания экрана с информацией о дате окончания подписки:

    import httpx
from hammett.template import render_template_from_string


response = await httpx.AsyncClient().get(
    'https://some/url/path/to/get/subscription/end/date/',
    params={'user_id': update.effective_user.id}
)
description = render_template_from_string(
    'The subscription ends on: {{date}}.', {
        'date': response.json()['date'],
    },
)

    Помимо переменных в шаблоне могут содержаться управляющие конструкции (control structures). Управляющая конструкция относится ко всем элементам, которые контролируют поток программы — условным операторам (таким как if/elif/else), циклам for, а также к таким вещам, как макросы и блоки. При использовании стандартного синтаксиса управляющие конструкции располагаются внутри блоков {% ... %}. Читайте подробнее, как использовать управляющие конструкции в шаблонах в статье Template Designer Documentation.

    Примечание: функция render_template_from_string является безопасной, т.е. если в шаблоне будет переменная, значение которой не указано в контексте или наоборот — значение указано для переменной, которая опущена в шаблоне, то переменная без значения не отобразится, а лишнее значение в контексте будет проигнорировано. Другими словами, функция не выбросит исключение, если произойдет рассинхрон между шаблоном и контекстом.

    Журналирование#

    Hammett использует и расширяет модуль logging из стандартной библиотеки Python, чтобы предложить разработчикам ботов гибкий и мощный инструмент журналирования.

    По умолчанию используется уровень журналирования INFO. Для того чтобы его переключить на другой уровень (например, DEBUG), в модуле settings.py нужно сконфигурировать свой объект LOGGING с нужным уровнем журналирования. Вот конфигурация журналирования по умолчанию:

    DEFAULT_LOGGING = {
    'version': 1,
    'disable_existing_loggers': False,
    'formatters': {
        'standard': {
            'format': '{levelname}: {name}: {asctime}: {message}',
            'style': '{',
        },
    },
    'handlers': {
        'console': {
            'formatter': 'standard',
            'level': 'INFO',
            'class': 'logging.StreamHandler',
        },
    },
    'loggers': {
        'hammett': {
            'handlers': ['console'],
            'level': 'INFO',
        },
    },
}

    Ниже приведен пример конфигурации журналирования, в котором уровень устанавливается с помощью переменных окружения LOG_LEVEL_CONSOLE и LOG_LEVEL_HAMMETT.

    import os


LOGGING = {
    'version': 1,
    'disable_existing_loggers': False,
    'formatters': {
        'standard': {
            'format': '{levelname}: {name}: {asctime}: {message}',
            'style': '{',
        },
    },
    'handlers': {
        'console': {
            'formatter': 'standard',
            'level': os.getenv('LOG_LEVEL_CONSOLE', 'INFO'),
            'class': 'logging.StreamHandler',
        },
    },
    'loggers': {
        'hammett': {
            'handlers': ['console'],
            'level': os.getenv('LOG_LEVEL_HAMMETT', 'INFO'),
        },
    },
}

    Вот так теперь можно использовать журналирование в боте:

    import logging

LOGGER = logging.getLogger(__name__)

LOGGER.debug('The user %s (%s) has moved to the MainMenu screen.', user.username, user.id)

LOGGER.info('The user %s (%s) was added to the admin group.', user.username, user.id)

    Debug-режим#

    При включении debug-режима Hammett автоматически журналирует смену состояний в ходе работы с ботом: с какого состояния на какое был осуществлен переход и с помощью какого обработчика. Например, вот так будут выглядеть логи после перехода из DEFAULT_STATE в YET_ANOTHER_STATE:

    DEBUG: hammett.core.conversation_handler: 2025-01-01 00:00:00: Switched to `yet_another_state` state from `0` state via `YetAnotherScreen.move_along_route` handler.
DEBUG: hammett.core.conversation_handler: 2025-01-01 00:00:00: Switched to `0` state from `yet_another_state` state via `MainMenu.move` handler.

    Эта информация может оказаться полезной в тех случаях, когда не совсем очевидно, почему не удается вызвать тот или иной обработчик.

    Start-маркеры#

    В комплексных ботах нужно средство для отслеживания источников, из которых пользователи попадают в ботов. Для решения этой задачи Hammett предлагает так называемые start-маркеры — механизм, позволяющий передавать Telegram-боту информацию в формате key=value прямо в ссылке на бота. К примеру, для разных каналов распространения нашего бота TurorIn.Tech мы используем разные ссылки, чтобы отслеживать эффективность каждого из этих каналов. Когда мы предлагаем ссылку на бота через Instagram stories, то она выглядит так:

    https://t.me/TutorInTechBot?start=instory

    Ссылка в био нашей Instagram-страницы, в свою очередь, выглядит так:

    https://t.me/TutorInTechBot?start=inbio

    Механизм представлен классом StartMarker из модуля hammett.start_marker. При создании объекта конструктору следует передавать текст введенного сообщения, который содержится в update.message.text. Если пользователь перешел в бота по одной из указанных выше ссылок, этот объект будет содержать текст, идущий за ?start=.

    Примечание: важно проверять, что update.message не является None, что случается при редактировании предыдущих сообщений.

    К примеру, пользователь перешел в бота по ссылке https://t.me/TutorInTechBot?start=instory. Вот реализация простого обработчика команды /start, в котором можно получить текст, идущий за ?start=:

    from hammett.core import Screen
from hammett.core.constants import DEFAULT_STATE
from hammett.core.mixins import StartMixin
from hammett.start_marker import StartMarker


class MainMenu(StartMixin, Screen):
    async def start(self, update, context):
        if update.message is None:
            return DEFAULT_STATE

        start_marker = StartMarker(update.message.text)
        start_marker['source']  # содержит 'instory'
        ...

    Как видите, объекты StartMarker поддерживают интерфейс словаря: используйте в качестве ключей названия start-маркеров. Start-маркером по умолчанию является 'source'. На первый взгляд может показаться запутанным, что ключ называется source, а не start, но изначально механизм разрабатывался именно для отслеживания источников (sources), из которых пользователи попадают в ботов, поэтому название source для первого start-маркера выглядит оправданным.

    Вы можете передавать в ссылке на бота любое количество пар ключ-значение. Например, в нашем боте мы можем одновременно отслеживать источник, из которого пользователь попал в бота, и получать информацию, на какую книгу его сразу переадресовать (да, бот представляет собой библиотеку книг):

    https://t.me/TutorInTechBot?start=instory=book=37

    start_maker['book']  # содержит '37'

    Как видите, знак = используется в обоих случаях: в качестве разделителя ключа и значения, а также в качестве разделителя пар ключ-значение. Это может сбивать с толку в начале, но совсем скоро вы проникнетесь красотой этого решения.

    Настройки сетевого интерфейса#

    Чтобы управлять максимальным временем ожидания ответа от сервера Telegram (в секундах) при отправке сообщений, можно воспользоваться параметром конфигурации SEND_METHODS_READ_TIMEOUT. По умолчанию его значение равно 5 секундам.

    Чтобы управлять максимальным временем ожидания ответа от сервера Telegram глобально, можно воспользоваться параметром конфигурации APPLICATION_BUILDER_READ_TIMEOUT. По умолчанию его значение равно 5.0 секундам.
